## Conformance notes

_The notebook declares NOTEBOOK_SPEC 2.2 (`metadata.dimer.notebook_spec = "2.2"`). The identifiers `ST1`–`ST6`, `ENV2`, `ENV6`, `EVAL9`, `EVAL11`, `RUN1`, `RUN10`, `REL1`, `REL8`, `REL11`, `DAT12` and `UX10` below are 2.2 identifiers. `PAR1`–`PAR4`, `DAT22`–`DAT24`, `EVAL21`, `MOD12`, `SEC11`, `ENV11` and `ENV12` are older identifiers these notes were first written against; 2.2 has no identifier of the same name, and they are kept only to name the check._

- **Standalone carrier (ST1–ST6):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/kokoro_tts_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 58-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins and the hash-locked requirements compiled from them. `metadata.dimer.generated_from` records the repository, the revision generated from, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/kokoro_tts_input_manifest.json` with the schema, ceilings, the request's character and segment counts, the voice/speed/language in force, the size of the verified voice inventory, the verdict and one recorded rejection finding (a British `bf_…` voice against an American `lang_code='a'` instance); `evaluation_report` (EVAL21) writes `outputs/kokoro_tts_evaluation_report.json`, whose verdict is always `not-measurable` because speech quality has no ground truth here — the report names the external judges (listener MOS, ASR round-trip WER) that would make the task measurable (EVAL9).
- The notebook exercises `KokoroTTSPipeline` carried verbatim in the notebook rather than reimplementing model loading; the pipeline pins the immutable upstream revision, stages the 55 git-ignored snapshot files (checkpoint plus 54 voice packs) through the package's `stage_missing_files(..., allow_download=True)`, loads only from a digest-verified local snapshot (`verify_snapshot`, all 58 manifest entries), and reads the voice list from that manifest (`list_voices`). No cell outside the carried module constructs `KModel`/`KPipeline` or calls `huggingface_hub`; `kokoro`, `misaki` and `soundfile` are imported only to report the pinned runtime identity and to write the WAV.
- Trust boundary (MOD12/SEC11): the checkpoint and voice packs are PyTorch pickles, not SafeTensors (`WEIGHT_FORMAT`); the notebook states before loading that digest verification runs first and that the library deserialises them with the weights-only loader (`LOADER_WEIGHTS_ONLY`), and that neither check makes an unverified pickle safe.
- No intrinsic metric exists (EVAL9): speech has no ground truth to score against; the repository ships no metric helper; the notebook says so, names the external judges a real evaluation needs (MOS from listeners, ASR round-trip WER with the judge named), and presents its structural sanity checks (dtype, rate, finite samples, peak within full scale, every non-blank line either voiced or reported as skipped) as plumbing checks only. The model card's smoke observation is quoted as one measurement, not an expected value. Recorded `SHOULD` deviation: EVAL11 (no baseline — none is meaningful for synthesis without a judge).
- Determinism (ENV11/ENV12): the vocoder is stochastic by default; the notebook seeds `torch.manual_seed(SEED)` immediately before `synthesize`, states that the seed controls one host and build only, and exports the seed.
- Ceilings `MAX_TEXT_CHARS`, `MIN_SPEED`/`MAX_SPEED`, `LANG_CODES`/`DEFAULT_LANG_CODE` (voice must match the loaded language), `SAMPLE_RATE` are surfaced before the model runs; how the library treats a long line (above 510 phonemes it is split into several chunks) and a line that phonemises to nothing (skipped; the notebook names it in a warning through `skipped_lines`) and the espeak-ng fallback (`espeak_fallback`, dropped out-of-dictionary words when absent) are explained, and the phoneme string is printed as the in-repository dropped-word check (DAT22/DAT23, DAT12).
- Isolated runtime (RUN1, RUN10, ENV6, REL11): `kokoro` 0.9.4 and `misaki` 0.9.4 declare `Requires-Python <3.13`, so they cannot be installed into Colab's Python 3.13 kernel, and an in-kernel install on a 3.12 kernel replaced pre-imported NumPy/torch and needed a restart. Section 1 now verifies a pinned `uv` wheel, creates a managed CPython 3.12.12 environment and installs `tutorials/requirements-colab.lock.txt` with `--require-hashes --only-binary :all:`; the router sends every later cell there. The lock is compiled from the `pyproject.toml` pins constrained to the versions of `ast-audio-classification-pipeline`'s T4-passed lock (`16eee39`; all 47 of its packages at the same versions) plus the `kokoro`/`misaki` spaCy stack. Wheel-only resolution selects `num2words` 0.5.6 (newer releases depend on the sdist-only `docopt`).
- spaCy model (ENV2): `misaki` needs `en_core_web_sm`; instead of the runtime `pip` download `misaki` would attempt (the `uv` environment has no `pip`), the 3.8.0 wheel is in the lock with its SHA-256, fetched from its GitHub release in Section 1. No system package is required: the `espeakng-loader` wheel bundles the espeak-ng library.
- The default sample is synthetic text authored in code; `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog. With BYOD on, `BYOD_PATH` works on any runtime, and a cancelled upload, a runtime without the Colab dialog, a missing path and a non-UTF-8 file each stop with a message naming the fix (UX10).
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
